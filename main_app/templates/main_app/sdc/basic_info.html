The ShuttleBuilder is a service that allows you to create and manage your Shuttle instances. It operates independently of the Electronic Lab Notebook (ELN) Chemotion.
However, if a ShuttleBuilder instance is configured as part of a Chemotion setup, it can function as a Chemotion service. Users can log in using their Chemotion username and password. (Admin interface)
In addition, users can register to create local accounts, or an administrator can create local users. (Admin interface)

The physical separation of laboratory PCs from public networks for security reasons significantly impacts the file transfer process requirements. Consequently, data stored locally on lab devices must be forwarded to the ELN via an intermediary system. The Shuttle is one part of such an intermediary system. It can facilitate this by sending device data to an intermediary data storage. It allows you to monitor and organize the data transmission of devices integrated with your ELN Chemotion instance (for more information, click here ). Shuttle instances can be quickly and easily adapted to specific requirements. These instances can then be installed on the target lab system in just a few steps.

How to install Shuttle

The following section introduces the installation of the Shuttle. Note that the installation is only intended for Windows (x64, and i386 incl. Windows XP) and Linux (x64 and Raspberry Pi) devices.

  1. Generate Shuttle instance:

    In Shuttle list you will find a new button. With this button you can create a new Shuttle instance adapted to an external WebDAV or SFTP server, or to a ChemAssistentManager job (see ChemAssistent upload below).

  2. Download Shuttle instance:

    After you have created a new Instance you can download the executable in the Shuttle list.

  3. Install Shuttle instance:
    • Install Shuttle instance:

      The installation is simple but requires administration rights.

      1. Make a directory "C:\Program Files\Shuttle"
      2. Copy the (on this server generated) shuttle.exe into "C:\Program Files\Shuttle" (a zip file contains an INSTALL.txt with these steps; copy all its files)
      3. Copy the shuttle_task.vbs into the startup directory.

        Hint: Press Windows Key + R to open run and type shell:startup. This will open startup directory

    • (SPECIAL CASE) Install Shuttle with SFTP on Windows XP:

      As above the installation requires administration rights. The "Download" button leads to a zip file and not only to an executable file. This zipped file contains the executable file and WinSCP. The SSH host key of the server is required for this case (see Security options); it is compiled into shuttle.exe. SFTP on Windows XP has not been tested on a real Windows XP machine yet. For WebDAV, XP verifies the server only if a server certificate is given.

      1. Make a directory "C:\Program Files\Shuttle"
      2. Unzip the downloaded file shuttle_sftp_winxp.zip
      3. Copy all files (shuttle.exe, WinSCP.exe, WinSCP.com, license.txt) into "C:\Program Files\Shuttle". WinSCP must stay next to shuttle.exe.
      4. Copy the shuttle_task.vbs into the startup directory.

        Hint: Press Windows Key + R to open run and type shell:startup. This will open startup directory

    • Install Shuttle on LINUX:

      As above the installation requires administration rights. This installation description works only for systemd

      1. Make a directory "/opt/Shuttle"
      2. Copy the shuttle executable (for a zip: all its files) into "/opt/Shuttle/" and make it executable
      3. Set the field Linux user of the instance (the user whose home holds the working folder). In the Shuttle list use the systemd unit button of the instance to download shuttle.service (fallback: the generic shuttle.service). If it contains User=CHANGE_ME, replace it with the Linux user. Copy it into /etc/systemd/system/shuttle.service and run systemctl daemon-reload and systemctl enable --now shuttle.service.

    {% trans "First start, working folder and log" %}

    Shuttle keeps its log (shuttle_log.txt), the list of sent files (sent_register.json) and known_hosts (SFTP) in ~/shuttle/shuttle_<name>/ (Windows: %USERPROFILE%\shuttle\shuttle_<name>\). The user is the one who runs Shuttle (Linux: Linux user of the instance). The log is also written to the standard output (on Linux with systemd: journalctl -u shuttle.service).

    • On the first start Shuttle sends every stable file already in the source folder (not changed for the configured duration) once. Plan for the traffic and for duplicates on the server.
    • Afterwards a file is sent when it is new or changed. A folder (types folder, zip, tar) that changed is sent again completely.
    • To send everything again, stop Shuttle, delete sent_register.json and start Shuttle again.
    • If the server cannot be reached (also right after booting the PC), the error is logged and the upload is retried with increasing waits. Files stay in the working folder until the upload is confirmed.
    • Update: download the Shuttle again, replace the executable and restart Shuttle. An existing sent_register.json is kept; when you update from Shuttle 1.12 or older, the data in the source folder is uploaded again.

Security options

  • SSH host key (SFTP only): fingerprint of the server (SHA256:... or MD5:aa:bb:...), e.g. from WinSCP (Session, Server/Protocol Information) or ssh-keyscan -p <port> <host> | ssh-keygen -lf -. With a host key, Shuttle only connects to a server that presents exactly this key. Without it, the key seen on the first connection is trusted and stored in known_hosts; if the server later presents a different key, Shuttle refuses to connect. It is required for Windows XP with SFTP and applies to both SFTP destinations.
  • Server certificate (WebDAV and ChemAssistent): PEM file for self-signed servers. It is delivered as server.crt inside a zip file next to the executable; keep it there. Shuttle verifies the server certificate with the system certificates plus this file. On Windows XP this file is the only way the server is verified. After adding a certificate, download the zip again.
  • Disable verification (insecure): turns off TLS and SSH host key verification. Only for tests; such instances are marked in the Shuttle list and Shuttle logs a warning at start.

ChemAssistent upload

The transfer type ChemAssistent job (HTTP upload) sends each file (or folder) to a ChemAssistentManager job by HTTP POST. Every upload starts one run of the job's AI agent, which gets the files as input.

  1. In ChemAssistentManager create a job with the trigger "HTTP file upload (API key)" and create an API key for it. The key is shown only once.
  2. Create the Shuttle instance with the transfer type ChemAssistent job (HTTP upload): enter the server URL as destination and the API key (cam_...). The user, the SSH host key and the converter are not used.
  • The destination is http:// or https:// with a host. Without a path (or with /) /api/jobs/trigger is appended; any other path is used as the full trigger URL.
  • Runs: file and flat_tar one run per file, zip and tar one run per archive, folder one run per folder. Folder paths are flattened into the file names (A/B/x.csv becomes A__B__x.csv).
  • Uploads larger than 100 MB are not attempted and stay local. A file is deleted locally only after the server confirmed the upload.
  • If the API key is revoked or the job is disabled, the files wait locally. Give the instance a new key, build and download it again and replace the Shuttle on the PC.
  • Server certificate and insecure work as for WebDAV. Windows XP speaks at most TLS 1.2; the server must offer TLS 1.2.

Shuttle version

The Git list shows the Shuttle version of every repository. The Shuttle list shows the version each instance was built with; the tooltip of the download button shows the version of the active repository.

  • Make sure the task scheduler is pointing to the correct executable file in the correct location
  • After restarting the computer, check from Task Manager if the schedule task is created and the application process is running
  • After editing the scheduling script, the computer needs to be restarted

Preprocess Scripts

Shuttle supports preprocess scripts, which allow you to execute custom scripts before transferring files. The rules (which files run, order, failures) are described on the page Preprocess scripts.

  • Windows: only regular files with the extension .exe are run (not .bat, .cmd or .sh).
  • Linux: every regular file with an execute bit is run, whatever its extension.
  • The folder is ~/shuttle/scripts (Windows: %USERPROFILE%\shuttle\scripts); it is created when Shuttle starts for the first time.

Such a script can manipulate the file before it is sent. The script is called for each file that will be sent. The script gets one argument with the absolute path to the file. The script should either overwrite the file or write a new copy of the file in the same folder.

Large data files

If the data files are too large, it is possible to configure the shuttle to convert the data and only send the converted Bagit archive to Chemotion. The original raw file can then be sent to a different storage location for archiving. See Preprocess scripts for the converter.

{% trans "Troubleshooting" %}

Start with the log: shuttle_log.txt in the working folder (see above). Lines starting with ERROR: are problems, lines starting with -> INFO: are information. Network problems are never fatal: Shuttle retries with increasing waits (1 second, doubled after every failed cycle, at most the configured duration) and no file is deleted before its upload is confirmed. Messages that make Shuttle stop at start (startup check failed and invalid settings) are printed on the console / standard error and are not written to shuttle_log.txt; on Linux look at journalctl -u shuttle.service.

Message in the logMeaning and what to do
Error connecting to destination (will retry): ... The server could not be reached at start (e.g. the PC booted before the network was up). Nothing is lost; Shuttle retries. If it persists, check destination, user, password, firewall and, for WebDAV/TLS, the certificate.
transfer failed 3 cycle(s) in a row, waiting 4s Uploads fail; Shuttle waits longer after every failed cycle. The error just above in the log tells why.
sending <path> was not confirmed The server did not confirm the upload. The local copy is kept and sent again later.
SSH host key for <host> CHANGED (presented SHA256:...). If the server key was changed on purpose, remove the line for <host> from <known_hosts> or set -hostkey The server presents another key than the one trusted on the first connection. Shuttle refuses to connect. If the server was reinstalled on purpose, delete the line of the server from known_hosts in the working folder, or enter the host key in the instance and download Shuttle again. If you do not expect a change, ask the server admin before you continue.
SSH host key mismatch for <host>: expected "<fingerprint>", server presented SHA256:... The host key entered in the instance does not match the server. Compare it with the fingerprint from the server admin, correct the instance and download Shuttle again.
trusting new SSH host key SHA256:... for <host> (stored in <known_hosts>) Information, not an error: no host key was given, so the key of the first connection is trusted. Compare the fingerprint with the one of the server if you want to be sure.
WARNING: TLS certificate verification is DISABLED (-insecure) and SSH host key verification is DISABLED (-insecure) The instance has Disable verification (insecure) set. Use it only for tests.
WARNING: Windows XP build without -crt: TLS certificate verification is DISABLED. Pass the server certificate with -crt to enable it. Windows XP, WebDAV, no certificate in the instance. Add the server certificate to the instance and download the zip again.
WARNING: cannot read -crt file <path>: ... or WARNING: no certificate found in -crt file <path> The certificate server.crt is missing next to the executable or is not a PEM certificate. Copy all files of the zip into the install folder. Uploads to a self-signed server fail until this works.
WinSCP.com not found, expected at <path>: ... Windows XP with SFTP: WinSCP.com (and WinSCP.exe) must be in the same folder as shuttle.exe.
winscp failed: ...; output tail: ... WinSCP could not upload; the end of its output follows. Typical: wrong host key, user or password, or the server is not reachable. The password is not written to the log.
no -hostkey given; WinSCP must already know the server's host key (accept it once in WinSCP), otherwise every upload fails Windows XP with SFTP and no host key. Enter the host key in the instance, or connect once with WinSCP on this PC and accept the key.
startup check failed: scripts folder <path> is not readable: ... Shuttle stops. Make the folder ~/shuttle/scripts readable for the user that runs Shuttle.
startup check failed: converter executable does not exist: <path>: ... The instance uses the converter; Shuttle stops. ChemConverterApp (ChemConverterApp.exe on Windows) must be next to the Shuttle executable.
conversion skipped: ... The converter could not be run for this file. The conversion is skipped, the raw data is still sent.
Sent register: 0 entries loaded, empty register: all stable files will be sent once Information: first start (or the register was deleted). All stable files in the source folder are sent once.
sent register corrupt: ... The register was damaged. It is moved aside as sent_register.json.corrupt-<time> and Shuttle starts with an empty register, which sends all stable files once more.
