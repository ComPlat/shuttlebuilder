Shuttle scripts

Files can be edited before sending. To use this logic, simply place the necessary executable file (the script) in a folder reserved for this purpose.

  • Linux: ~/shuttle/scripts
  • Windows: %USERPROFILE%\shuttle\scripts

The folder is the home of the user who runs Shuttle. It is created automatically when Shuttle starts, and it is shared by all Shuttle instances of that user. If it cannot be read, Shuttle does not start (startup check failed: scripts folder ... is not readable).

{% trans "Which files are run" %}

  • Windows: only regular files with the extension .exe (any case). .bat, .cmd and .sh files are not run.
  • Linux: every regular file with an execute bit (chmod +x), whatever its extension. A symbolic link to such a file is run too; a dangling link is skipped (skipping script link ... in the log).
  • Directories and hidden files (names starting with .) are never run; the .env file of the renamer below is just read by the script.
  • The scripts run one after the other in alphabetical order of the file names. To control the order, name them e.g. 01_first, 02_second.

{% trans "What a script gets" %}

Shuttle copies the finished file (or folder) first and runs the scripts on the copy. Every script is started with the folder scripts as working directory and receives the absolute path as its only argument. After all scripts have completed, all files from the folder where the original file was located are uploaded to the server. This means that the original file can be edited and overwritten, or new files can be created in the same folder.

{% trans "When a script fails" %}

  • If a script cannot be started or ends with an error, the error (for example exit status 1) is written to the log (shuttle_log.txt) and Shuttle continues with the next script. The file is still sent, in the state the scripts left it.
  • The output of each script (standard output and standard error) is written to the log after the script has finished, as <script name> |-> out: ... |-> err: .... Use it to debug a script.
  • Scripts are not stopped after a time limit: a script that never ends blocks the preparation of the next files.
File from content renamer

This Script reads a file and renames it based on its content. To use it you need to add a .env file into the script directory with the following keys.

The .env file

SFC_FILE_FILTER_RE=\.txt$
SFC_NEW_NAME_RE=^Data File Name\s+(.+)$

SFC_FILE_FILTER_RE is used as a filter. If this regexp matches the file will be renamend

SFC_NEW_NAME_RE is used to find the new name. This regex must have at least one group. The new name is the match of the first group

ShuttleFromContentRenamer (Linux) or ShuttleFromContentRenamer (Win)

The following ChemConverter is not a Script. It must not be used in the script directory. However, it can be set up as part of the shuttle in the instance edit/create form (With converter).

{% trans "Converter behaviour" %}

  • With a converter, Shuttle runs ChemConverterApp convert -i <path> -o jcampzip (Windows: ChemConverterApp.exe) after the scripts and sends the converted file to the second destination (BagIt, with the public link of the raw file).
  • The converter must be in the same folder as the Shuttle executable (the converter is only available for Windows 64 Bit and Ubuntu 64 Bit; their zip contains it). On Linux it needs the execute bit, on Windows the extension .exe; otherwise it is not run.
  • Converter missing at start: Shuttle stops with startup check failed: converter executable does not exist: <path>: .... Copy the converter next to the executable. This message is printed on the console / standard error, not into shuttle_log.txt.
  • Converter missing or failing later (for example deleted while Shuttle runs): the error is logged, for a missing converter as conversion skipped: converter executable does not exist: .... The conversion is skipped; the raw data is still sent. A converter that ends with an error is logged like a failing script (see above).
ChemConverter

ChemConverter is a file-format conversion service used in conjunction with the Chemotion Electronic Lab Notebook (ELN). Its main purpose is to standardize analytical data files — converting them into formats that Chemotion (and related tools like ChemSpectra) can display and work with.

How It Works Technically

ChemConverter has a three-layer architecture:
Reader layer:
Code that reads the incoming file format (TXT, CSV, DTA, etc.) and parses columns and values.

Admin profile layer:
Rules defined (by admins) for how to recognize and transform different input formats — based on file extension, header lines, column titles, or other identifiers.

Processing & Output:
The converter applies the selected profile, outputs standardized formats, and stores metadata and data in structures Chemotion understands.
