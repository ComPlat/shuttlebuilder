# ShuttleBuilder UI map

Generated by `manage.py sdc_teach` on 2026-11-19. Crawled as: anonymous, user teacher. All paths are relative to the site root.

## How to read SDC URLs

The app is a single page: the `sdc-navigator` shows nested views (SDC controllers) and the URL lists them.

- `/~parent-view~child-view~&key=value&other=2`: one controller tag per `~` segment, outermost first; every view is rendered inside the previous one. The part before the first `~` (usually `/`) is the Django page.
- The arguments start at the first `&` (or `?`): `key=value` pairs joined by `&`. Values are URL-decoded; numbers and `true`/`false` become numbers and booleans.
- A plain key belongs to the deepest view of the path. `N.key` belongs to the view at depth `N` (1 = first view): `/~book-list~book-edit~&1.page=2&pk=3` gives `page=2` to `book-list` and `pk=3` to `book-edit`. A view receives its arguments as `this.params` (`data-*` attributes; `camelCase` keys become `kebab-case`). The links of the current URL show the arguments with their depth (`2.pk=3`).
- Navigating keeps the arguments of the views above the opened view; the opened view gets only the arguments given.
- Relative paths are resolved against the current URL: `.` = the current path, `..` = one view up, `*` = keep the view at this depth, `..~other-view` replaces the deepest view, `.~child-view~&pk=3` opens a view below the current one. A path that does not start with `/`, `~`, `.` or `*` also opens below the current view (`book-edit` = `.~book-edit`).
- An empty path (`/`) opens the navigator's default controller; a view may open a default child view by itself.
- An unknown tag shows `sdc-error 404`; a view the user may not open shows `sdc-error 403`.
- `window.sdcNav.goTo(path, {key: value})`, the `goTo` event and links with the class `navigation-links` navigate without reloading the page (the AI assistant's `navigate` and `click` do the same). Opening the URL directly loads the whole page.

## How to operate this app

- Each view below is listed once, with the paths it was seen at; its links are resolved by the `sdc-navigator` (absolute paths with the arguments of their view depth).
- Buttons call controller methods named in their `sdc_click` attribute; "action:" is what the method does (its JSDoc), the text after the arrow is what the crawler observed when it clicked the button.
- Buttons marked "skipped" were not clicked by the crawler because they look destructive (delete, logout, save, submit); confirm with the user before clicking them.
- Forms were not submitted automatically: "submitted by developer" shows what a manual submit did, "not submitted" means the outcome is unknown.
- A view showing `sdc-error 403` needs a logged-in user with the right permissions.
- A view is ready when `window.sdcNav && !window.sdcNav._is_processing` and no `.sdc_sub_detail_container.loading` element exists.
- Server calls (`this.serverCall(...)`) execute methods of the matching `SDCView` on the server.
- All SdcModel WebSocket traffic (`/sdc_ws/model/<Model>`) was recorded per controller: "Model socket (on load)" lists what each controller requests when the view opens, buttons and forms list what they trigger, as `Model.event(args)` with the `model_query` filter keys. `connect` subscribes to live updates of the filtered rows; `load`, `save`, `create`, `delete`, ... read or write data.

## Common tasks

- Find a record: open the model's list (below) and fill its search bar, or read records with `model_load` and a filter; the record's id opens its detail or edit view.
- Create a record: open the model's create form, fill it; the user checks and submits it.
- Edit a record: open its edit form (`pk` = id) and fill it; the user checks and saves it.
- Delete a record: in the model's list, "Remove" in its row opens a dialog whose "Remove …" button deletes it; ask the user first, this cannot be undone.

Generic views per model (`<id>`: the record's id). A view that opens does not mean the role may see or change the records: that depends on the model's permissions (see Data models).

### `<sdc-navigator>`

Root navigation frame of an SDC app: owns the URL, the nested views and the breadcrumb; there is one per page and it is exposed as `window.sdcNav`.

- URL scheme: `/~<tag>~<child-tag>~&key=value&...`. Each `~` segment is a controller tag rendered nested inside the previous one; arguments after `~&` are passed to the views as data attributes (`N.key=value` targets only the view at depth `N`, plain `key` applies to the deepest one). Relative paths (`.`, `..`, `*` = keep the current segment at that depth) are resolved against the current path.
- An empty path opens the controller named in its `default-controller` argument; a view container with its own `data-default-controller` opens that child automatically.
- Links with the class `navigation-links` are handled client-side without page reload; `window.sdcNav.goTo('<path>', {args})` (or triggering the `goTo` event) navigates programmatically. Browser back/forward works.
- An unknown tag in the path shows `sdc-error 404` instead of the view. A view whose `allowedPaths` do not match the views in front of it shows `sdc-error 403` ("Not allowed"), e.g. `/~settings` for a view only allowed below `dashboard`. Some containers open their view in a modal; closing the modal navigates back one level.
- Links marked as login-only/logout-only are shown or hidden depending on whether a user is logged in; the `login`/`logout` events reload the whole page.

_app `sdc_tools`, server view `sdc_tools.sdc_views.SdcNavigator`, Django URL `/sdc_view/sdc_tools/sdc_navigator`_

### `<sdc-search-view>`

Search and paging bar embedded at the top of a model list (inside `<sdc-list-view>`); its fields come from the model's server-side search form.

Changing a search field filters the surrounding list immediately (no submit button needed). "Prev"/"Next" page through the results and the bar shows the current range and total count; the paging controls are hidden when everything fits on one page. It changes no data.

_app `sdc_tools`, server view `sdc_tools.sdc_views.SdcSearchView`, Django URL `/sdc_view/sdc_tools/sdc_search_view`_

### `ElnConnection` (main_app)

Connection to a Chemotion ELN server whose accounts may log in to the ShuttleBuilder.

- Users who log in with Chemotion credentials get a local account; new ones become staff if they are Chemotion admins.

### `ElnUser` (main_app)

Per-user profile that records whether a user logs in through the connected Chemotion ELN.

- One record per Django `User` (`user`, one-to-one); created automatically when a user is created.
- `is_eln_user`: `true` if the last login was verified by the active `ElnConnection`, `false` for a local account login.
- `token`: Chemotion API token from the last ELN login; empty for local logins.

### `GitInstance` (main_app)

A git repository (and branch or commit) holding the Shuttle source code that executables are built from.

- `name`: unique, cannot be changed later; `url`: clone URL; `branch`: branch name or commit id (default `main`).
- `is_active`: exactly one repo is active; all Shuttle builds use it. Activating a repo makes it the source of every later build.
- `last_reload`: when the repo was last cloned (`git clone`, then `git checkout <branch>`); `null` means it is cloned on the next build. A failed clone or checkout raises an error and keeps the previous checkout.
- `shuttle_version`: version of the Shuttle in the checkout (`shuttleVersion` in `main.go`), read after every successful reload; empty if it cannot be found. Shown in the git list (`<git-instance-list>`), also as the version a download will build (tooltip of the download button in the Shuttle list).
- If none is active, the default `ComPlat/shuttle/Main` (https://github.com/ComPlat/shuttle.git, `main`) is created and activated.
- Rolling out a new Shuttle version: reload the active repo (or activate another one). Afterwards every `ShuttleInstance` is rebuilt on its next download (its `built_version` then shows the new version); the lab downloads the Shuttle again, replaces the executable and restarts it. Already installed Shuttles are not updated by themselves.
- Builds use the toolchains of the server image: Go 1.26.11, and Go 1.10.8 (`XP_GOROOT`) for Windows i386 (Windows XP).
- Readable and editable by every logged-in user.
- Listed and activated in `<git-instance-list>`, created/edited in `<git-insatnce-edit>`.

Fields: `id` (BigAutoField), `name` (CharField), `url` (CharField), `branch` (CharField), `is_active` (BooleanField), `last_reload` (DateTimeField), `shuttle_version` (CharField)

### `ShuttleInstance` (main_app)

Configuration of one Shuttle: a small program for a lab PC that watches a folder and uploads new data (WebDAV or SFTP).

Fields:
- `name`: unique, cannot be changed later; also the name of the working folder `~/shuttle/shuttle_<name>/` on the lab PC. `owner`: the creating user. Logged-in users see and change only their own instances; staff and superusers see all.
- `src`: folder to watch on the lab PC (entered plainly, no doubled backslashes); `duration`: seconds a file must stay unchanged before it is sent (default 300, at least 1; it is also the longest wait between retries).
- `transfer`: `webdav` or `sftp`; `dst`, `user`, `password`: target URL and credentials on the server. `dst` is checked: SFTP `host[:port]/path` (also `ssh://` or `sftp://`, port 22 by default), WebDAV `http(s)://host/path`.
- `shuttle_type`: `file` (each file), `folder` (whole folder once complete), `zip` / `tar` (folder as an archive once complete) or `flat_tar` (files grouped by the `common_name_parts` regex into .tar.gz archives). A changed folder is sent again completely.
- `architecture`: target system: `win_i386` (also Windows XP), `win_64`, `ubuntu_64`, `raspberry_pi_6`, `raspberry_pi_7` or `raspberry_pi_64`. Windows i386 is built with Go 1.10.8, everything else with Go 1.26.11.
- `with_converter`: also convert data with ChemConverterApp to a BagIt archive, sent to `dst_bagit` with `user_bagit`/`passwort_bagit`; needs a JSON `profile`, `public_link` is the URL prefix of the raw files. The converter ships in the zip (Windows x64, Linux); a failing conversion is skipped and the raw data is still sent.
- `host_key` (SFTP only): expected SSH host key fingerprint of the server, `SHA256:<base64>` (optionally `ssh-ed25519 255 SHA256:...` as shown by WinSCP) or MD5 `aa:bb:...`. It applies to both SFTP destinations, so with a converter both must be the same server. Required for `win_i386` + SFTP unless `insecure` is set. Otherwise empty means trust on first use: Shuttle stores the key of the first connection in `known_hosts` and refuses a changed key later.
- `cert` (WebDAV only): PEM server certificate (`.crt`, `.pem`, `.cer`), needed for self-signed servers and the only way TLS is verified on Windows XP. It is built in as `server.crt` and shipped next to the executable (the download becomes a zip).
- `insecure`: WARNING, disables TLS certificate **and** SSH host key verification. Any user may set it; use it only for tests. It is flagged ("Verification disabled") in the instance list and Shuttle logs a warning at start.
- `linux_user`: the Linux user that runs the service; used in the systemd unit of the instance. Empty: the unit contains `User=CHANGE_ME` to replace by hand. Ignored for Windows architectures.
- `built_version`: Shuttle version of the last successful build, shown next to the download button (empty: not built yet). The active `GitInstance` version may be newer; the next download then rebuilds. `last_build`, `last_update`: set by the system.

Warnings shown in the instance list: "Verification disabled" (`insecure`) and "No host key" (SFTP without `host_key`: trust on first use).

Download and installation:
- Downloading compiles the executable from the active `GitInstance` (slow on first download or after changes); deleting also removes the build files.
- The download is the bare executable, or a zip when a certificate (WebDAV), a converter, or Windows XP + SFTP (with WinSCP) applies. Every zip contains `INSTALL.txt` with the install steps for the instance: install folder `C:\Program Files\Shuttle` (Windows, plus `shuttle_task.vbs` in `shell:startup`) or `/opt/Shuttle` (Linux), working folder and log (`shuttle_log.txt`), the sent register (`sent_register.json`; the first start sends every stable file in `src` once) and `known_hosts`. `INSTALL.txt` contains no secrets.
- Linux: the instance list has a "systemd unit" button (per-instance `shuttle.service`, owner/staff only); install it as `/etc/systemd/system/shuttle.service`, then `systemctl daemon-reload` and `systemctl enable --now shuttle.service`. A generic unit without user exists for old links.
- Listed in `<shuttle-instance-list>`, created/edited/copied in `<shuttle-instance-edit>`.

Fields: `id` (BigAutoField), `name` (CharField), `user` (CharField), `password` (CharField), `transfer` (CharField), `src` (CharField), `dst` (CharField), `shuttle_type` (CharField), `common_name_parts` (CharField), `duration` (PositiveIntegerField), `host_key` (CharField), `cert` (FileField), `insecure` (BooleanField), `architecture` (CharField), `with_converter` (BooleanField), `user_bagit` (CharField), `passwort_bagit` (CharField), `dst_bagit` (CharField), `public_link` (CharField), `profile` (FileField), `last_update` (DateTimeField), `last_build` (DateTimeField), `linux_user` (CharField), `built_version` (CharField), `owner` → `SdcUser`
